## Problem

The accepted initial-onboarding Design deliberately guarantees only:

- one Draft root record;
- one active onboarding Task;
- one navigable knowledge map;
- one unconfirmed current-system Realization; and
- for Technology, one required Draft Specification.

The native NKF 0.1 Specification treats directories under `knowledge_root` as
navigation and currently says they should exist only when real material needs
them. The adopter therefore generates only those minimum files and preserves
existing paths instead of establishing a complete lifecycle topology.

ADR 0053 establishes the fuller Task, Design, Decision, Specification,
Realization, and Evidence organization only for the NKF repository. Its scope
does not make that organization a portable NKF Core or Root Profile
requirement.

Nourd Agent SDK consequently received a structurally conformant but minimal
Draft scaffold. Because its existing `knowledge/README.md` occupied the
default map path, the adopter also generated `knowledge/README-2.md` rather
than reconciling one canonical knowledge map. This is valid under the current
implementation but fails the intended onboarding experience.

## Finding Classification

This is primarily an NKF Specification and onboarding-contract gap. Depending
on the accepted topology boundary, realization will also require coordinated
adopter, checker, fixture, test, documentation, release, and migration work.

It is not an Agent SDK nonconformance and is not evidence that the onboarding
agent ignored the accepted contract. The agent and adopter produced the
minimal output currently required by NKF.

## Desired Outcome

Every supported initial Product or Technology onboarding produces one
complete, predictable, human-navigable, agent-navigable, and mechanically
enforceable knowledge topology.

The topology must distinguish the shared portable lifecycle structure from
Product- or Technology-specific additions. It must work for an effectively
empty repository and for a Tiny Knowledge repository with existing paths,
without inventing acceptance, rewriting history, losing provenance, or
creating duplicate navigation roots.

Successful onboarding must still create Draft and unconfirmed meaning. A full
directory structure cannot make empty lifecycle areas authoritative, accept
documents, adopt Designs, confirm Realizations, or make Governing Use ready.

## Scope

- define the exact portable baseline topology shared by Product and
  Technology repositories;
- define additive Product and Technology topology requirements without a
  selectable Generic profile;
- decide how Tasks expose Active, Deferred, and Completed navigation;
- decide how Designs expose Active, Adopted, Rejected, Superseded, and
  Withdrawn disposition navigation;
- define canonical Decision, Specification, current Realization, Evidence,
  and knowledge-map locations;
- decide whether required directories contain declared navigation indexes,
  another version-controlled artifact, or are created only when populated;
- reconcile the current Specification rule that directories should exist only
  when real material needs them;
- define one canonical knowledge-map collision and merge policy so onboarding
  does not generate names such as `README-2.md` merely because `README.md`
  already exists;
- preserve existing consumer bytes, authority, document identity, relative
  links, history, and unresolved meaning during topology reconciliation;
- define how every generated Markdown navigation file is represented in
  `.nourd` and receives the required frontmatter and UTC timestamp;
- define which topology properties the checker enforces after adoption rather
  than leaving the structure as a one-time generator convention;
- update onboarding plan, sealing, transaction, rollback, receipt, status,
  and idempotence behavior for the accepted structure;
- define deliberate migration for repositories already onboarded with the
  minimal NKF-013 or NKF-015 scaffold;
- update Product and Technology fixtures, tests, public documentation,
  adopter distribution, release bindings, and compatibility guidance; and
- independently audit and confirm the exact successor before release.

## Required Design Decisions

1. Which lifecycle directories and navigation indexes are mandatory portable
   NKF Core structure?
2. Which additions belong only to Product or Technology Root Profiles?
3. Does complete topology require physical version-controlled content for
   currently empty lifecycle areas, and if so what non-authoritative
   navigation representation is used?
4. Is the topology only an onboarding output requirement, or a continuing
   conformance requirement enforced by the checker?
5. How does onboarding reconcile an existing knowledge map, lifecycle
   directory, conflicting filename, or partial topology without silently
   overwriting consumer meaning?
6. Which source becomes the canonical map when a repository already has
   `knowledge/README.md`?
7. How are existing flat Tasks and Designs proposed for movement without
   inferring Task state or Design disposition from filenames or prose?
8. Which changes are compatible pre-stable evolution within NKF `0.1`, and
   what deliberate consumer migration is required?
9. How should already onboarded repositories reach the corrected topology
   without rerunning semantic category assessment or pretending the original
   onboarding never occurred?

Resolve these boundaries with the Human Product Owner one consequential
decision at a time. Do not infer the final topology from the NKF repository's
local ADR 0053 organization.

## Acceptance Criteria

- A Human Product Owner Decision accepts the exact portable Common, Product,
  and Technology topology and its navigation semantics.
- The canonical Specification and executable companion state whether each
  topology element is required at onboarding, continuously required for
  conformance, or optional until populated.
- Both supported Root Profiles receive the accepted complete baseline while
  retaining their distinct root meaning and requirements.
- Existing `knowledge/README.md` content is reconciled deliberately into one
  canonical map; the normal path does not generate `README-2.md` or another
  arbitrary collision suffix.
- Every generated Markdown source has truthful frontmatter, a real UTC
  `created_at`, and exactly one record declaration or explicit `non_records`
  representation.
- Empty lifecycle areas remain visibly non-authoritative and cannot imply
  acceptance, Design adoption, Task completion, Specification authority, or
  Realization confirmation.
- Existing consumer bytes, links, identity, provenance, authority, and
  unresolved meaning survive onboarding and migration.
- The checker fails closed for every topology property the accepted contract
  makes continuously mandatory.
- Fixtures and tests cover Product and Technology, Empty and Tiny Knowledge,
  existing and partial topology, map collision, unsafe paths, rollback,
  idempotence, and predecessor migration.
- Public guidance explains the complete created topology, ownership of every
  area, and the distinction between scaffold presence and semantic authority.
- A deliberate migration path repairs repositories created by the minimal
  NKF-013 and NKF-015 scaffold without rerunning category assessment or
  silently changing meaning.
- Independent audit Evidence records no unresolved material finding, and a
  separate Decision confirms the exact successor Realization before release.
